# HW_1_SOLUTION.md — Нагрузочное тестирование demo-app-1

## 1. Метрики — что и зачем отслеживаем

| Слой | Метрика | Почему важна | Источник |
|---|---|---|---|
| nginx | RPS, active connections, 4xx/5xx rate | Первая точка входа — здесь виден совокупный трафик и доля ошибок до app | nginx → prometheus (через `/metrics` proxy) |
| app server (Go) | `http_request_duration_seconds` (P50/P95/P99), `http_requests_total`, error rate | Показывает задержку бизнес-логики и частоту ошибок с разбивкой по endpoint/method | prometheus exporter в `main.go` |
| app server (Go) | `db_query_duration_seconds` | Отделяет время БД от времени CPU приложения; быстро указывает куда смотреть | prometheus exporter в `main.go` |
| PostgreSQL | `pg_stat_activity_count`, `pg_stat_database_tup_fetched`, `pg_locks_count` | Покажет исчерпание connection pool и блокировки при конкурентной записи | postgres_exporter (порт 9187) |
| PostgreSQL | `pg_stat_statements` query duration | Позволяет найти медленные запросы и добавить индекс | postgres_exporter + pg_stat_statements extension |
| Система | CPU %, RAM %, network I/O | Исключает hardware bottleneck; на Mac в Docker они ограничены ресурсами VM | node_exporter (порт 9100) |
| Контейнеры | `container_cpu_usage_seconds_total`, `container_memory_usage_bytes` | Позволяет видеть нагрузку на каждый сервис отдельно (backend vs db vs nginx) | cAdvisor (порт 8088) |
| k6 | `http_req_duration` P50/P90/P95, `http_req_failed`, RPS | Клиентская точка зрения — что видит пользователь | k6 встроенные метрики |

## 1★. Дополнительные метрики добавлены в код

Исходный `main.go` не давал видимости в connection pool и очередь запросов. Добавлено в `backend/main.go`:

| Метрика | Тип | Что показывает |
|---|---|---|
| `db_pool_open_connections` | Gauge | Общее число открытых соединений к postgres (in-use + idle) |
| `db_pool_in_use_connections` | Gauge | Соединения, занятые прямо сейчас выполнением запроса |
| `db_pool_idle_connections` | Gauge | Соединения в пуле, ждущие следующего запроса |
| `db_pool_wait_total` | Counter | Сколько раз запрос ждал свободного соединения — ключевой индикатор исчерпания пула |
| `db_pool_wait_duration_seconds_total` | Counter | Суммарное время ожидания свободного соединения |
| `http_requests_in_flight` | Gauge | Запросы в обработке прямо сейчас — показывает насыщение app-сервера |

**Почему именно эти:** исходный код использует `sql.DB` без `MaxOpenConns`, то есть пул неограничен. Новые метрики показывают реальное число открытых соединений в моменте — именно это нужно было видеть чтобы подтвердить гипотезу о connection exhaustion.

**Что видно под нагрузкой (800 VU, пик):**
```
db_pool_in_use_connections  925
db_pool_open_connections    927
http_requests_in_flight     982
db_pool_wait_total          0     ← пул без лимита, никто не ждёт
```

`db_pool_wait_total=0` при 927 открытых соединениях — Go спокойно открывает столько коннектов сколько нужно, но postgres при этом деградирует из-за context switching на >200 соединений. Именно поэтому нужен `db.SetMaxOpenConns()` + PgBouncer: поставить лимит на стороне приложения, чтобы очередь формировалась в памяти Go, а не в postgres.

## 2. Архитектура приложения

**Компоненты:**
- **nginx** (порт 8080) — reverse proxy, отдаёт статику из `ui/`, проксирует `/api/` и `/metrics` на backend
- **backend** (Go, порт 8081) — HTTP API, использует `gorilla/mux`, подключается к postgres напрямую через `database/sql`
- **postgres** (порт 5432) — единственное хранилище; две таблицы: `users` и `orders` (orders.user_id FK → users.id)
- **postgres_exporter** (порт 9187) — экспортирует метрики postgres в Prometheus
- **node_exporter** (порт 9100) — системные метрики хоста
- **cAdvisor** (порт 8088) — метрики контейнеров
- **prometheus** (порт 9090) — сбор метрик со всех источников (интервал 5s)
- **grafana** (порт 3000) — визуализация; дашборды для k6, Node Exporter, Postgres

**Цепочка запроса:**
```
k6 → nginx:8080 → backend:8081 → postgres:5432
                                       ↓
                             INSERT/SELECT orders/users
                                       ↑
                              ответ → backend → nginx → k6
```

**API endpoints** (все с префиксом `/api/`):
- `POST /api/orders` — создать заказ (user_id, amount, description)
- `GET  /api/orders` — список последних 100 заказов
- `GET  /api/orders/{id}` — заказ по ID
- `PUT  /api/orders/{id}`, `DELETE /api/orders/{id}`
- Аналогичный CRUD для `/api/users`

**Важно:** backend не использует пул соединений явно — `sql.DB` Go создаёт пул со значениями по умолчанию (`MaxOpenConns=0`, т.е. без ограничения), что приводит к проблемам при высокой нагрузке (postgres ограничен `max_connections=200`).

## 3. Сценарии нагрузки

### Сценарий 1: Шторм (storm)
- **Параметры:** резкий рост 0→1000 VU за 10 секунд, плато 30 секунд, снижение 10 секунд
- **Цель:** найти точку разлома под максимальным резким пиком; понять как ведёт себя система при внезапном 10-кратном всплеске трафика
- **Соотношение нагрузки:** 80% POST /api/orders, 20% GET /api/orders

### Сценарий 2: Волна (wave)
- **Параметры:** плавный рост 0→500 VU за 2 минуты, плато 1 минута, снижение 30 секунд
- **Цель:** проверить насколько планомерный рост лучше переносится системой по сравнению с резким пиком; найти устойчивый рабочий диапазон
- **Соотношение нагрузки:** 80% POST, 20% GET

### Сценарий 3: Пульс (pulse)
- **Параметры:** 3 пика по 300 VU (15 сек) с паузами 30 сек между ними
- **Цель:** проверить восстановление системы после каждого пика — возвращаются ли latency и error rate к baseline; смоделировать "прибой" трафика в течение дня

### Сценарий 1: Шторм — анализ

При резком нарастании до 1000 VU система потеряла **24.77% запросов**. P95 составил **6.93 секунды** — в 3.5 раза выше порога в 2 сек. Фактический RPS оказался всего **308 rps**, несмотря на 1000 параллельных VU — очевидно, что большинство VU стояли в ожидании.

**Гипотеза о причине:** Postgres ограничен `max_connections=200`. Backend Go открывает по соединению на запрос без ограничения пула. При 1000 VU все 200 слотов моментально заняты, новые запросы получают ошибку `too many connections` или зависают в ожидании, что объясняет и высокий error rate, и огромную latency. Часть ошибок — nginx 502 при таймауте backend.

### Сценарий 2: Волна — анализ

Плавный рост до 500 VU дал принципиально иной результат: **0.39% ошибок**, P95=**613ms**, фактический RPS=**695/s** — в 2.25 раза выше чем в storm несмотря на вдвое меньше VU. Это классический эффект: при плавном росте backend успевает обработать очередь, connection pool стабилизируется в пределах 200 соединений.

При ~450-500 VU появились единичные ошибки (0.39%) — это порог насыщения системы при текущей конфигурации connection pool.

### Сценарий 3: Пульс — анализ

Три пика по 300 VU с паузами 30 сек: **0 ошибок**, P95=**26.91ms**, avg=**17ms**. Система полностью восстанавливалась во время пауз. В промежутках RPS падал почти до нуля, latency — к минимальным значениям (~1.3ms median). Это подтверждает, что при умеренной нагрузке (300 VU) система работает в пределах нормы и не накапливает очереди между пиками.

## 5. Что видно на дашбордах Grafana

Grafana: `http://localhost:3000` (admin/admin). Datasource — Prometheus `http://prometheus:9090`. Дашборды импортированы из `dashboards/`. Метрики собираются каждые 5 сек; k6 пишет в Prometheus через remote write.

Ниже — что показывают три дашборда **во время каждого сценария**.

---

### Сценарий 1: Шторм (1000 VU, резкий пик)

**k6 Prometheus** (`/d/nNz4iDxDk`):
- **Request Duration** — резкий вертикальный скачок сразу после старта. P95 улетает до **6.93s** (k6) / **4.9s** (Prometheus, 1-минутное окно). Медиана — 1.64s. Форма кривой — почти прямоугольник: система мгновенно насытилась и держит высокую latency всё плато.
- **Request Rate** — парадокс шторма: при 1000 VU фактический RPS всего **308/s**, хотя wave при 500 VU даёт 695/s. Лишние VU не добавляют пропускной способности — они стоят в очереди к postgres.
- **Failed Requests** — пик **85% 5xx**. Это ошибки двух типов: `pq: sorry, too many clients` от postgres и nginx 502 при таймауте backend.

**Postgres Overview** (`/d/42kVmDbDz`):
- **Active Connections** — скачок до **142 одновременных соединений** из 200 допустимых. Само по себе не предел, но postgres при >100 соединениях начинает деградировать из-за context switching между процессами.
- **Query Duration** — P95 запроса к БД = **4937ms** ≈ P95 всего HTTP-запроса (4944ms). Вывод: **вся latency — это время в postgres**, Go-код занимает <1%.
- **Transactions/sec** — в начале пика кратковременный всплеск INSERT до **993 tps**, затем резкое падение: postgres перегружен и начинает отказывать.

**Node Exporter Full** (`/d/JKkVivxvk`):
- **CPU** — пиковая нагрузка **96.3%** (Docker VM, все ядра). Неожиданный инсайт: CPU — второй ограничитель после соединений. Postgres внутри контейнера форкает процесс на каждое соединение, 142 процесса одновременно насыщают CPU.
- **Memory** — **30.2%** (~1.2 GB / 3.9 GB). Памяти хватает с запасом, не узкое место.
- **Network** — короткий пик входящего трафика (~2 MB/s) в момент старта, затем снижение — новые запросы уже не доходят до backend из-за ошибок.

### Сценарий 2: Волна (0→500 VU, плавный рост за 2 мин)

**k6 Prometheus**:
- **Request Duration** — плавная нарастающая кривая. P95 достигает **613ms** на пике (500 VU) и медленно снижается при рампдауне. Никакого вертикального скачка — система успевает адаптироваться.
- **Request Rate** — стабильный рост до **695/s** и плато. В 2.25 раза выше storm при вдвое меньшем числе VU — потому что нет очереди, каждый VU реально работает.
- **Failed Requests** — **0.39%** ошибок, появляются только при ~450-500 VU — это порог насыщения пула при текущей конфигурации. До этого момента — идеальный 0%.

**Postgres Overview**:

- **Query Duration** — P95 на пике ~300-400ms — в 12 раз лучше чем при storm. БД справляется.
- **Transactions/sec** — ровное плато INSERT ~500-600 tps, стабильно без провалов.

**Node Exporter Full**:
- **CPU** — плавный подъём до ~40-50% на пике, без резких скачков. Система управляемо нагружена.
- **Network** — стабильный входящий поток **~1.7 MB/s** на всём плато (данные из k6 в 695 rps).

### Сценарий 3: Пульс (3×300 VU, с паузами 30 сек)

**k6 Prometheus**:
- **Request Duration** — отчётливо видны три прямоугольных пика на кривой latency, разделённых провалами до нуля. P95 в пике — **26.91ms**, в паузах — единицы миллисекунд. Система полностью восстанавливается за 30 секунд.
- **Request Rate** — три чётких пика ~400/s с нулями между ними. Форма графика — «заборчик».
- **Failed Requests** — **0.00%** на всех трёх пиках. При 300 VU система работает в зоне комфорта.

**Postgres Overview**:
- **Active Connections** — три кратковременных пика ~20-30 соединений, между ними возврат к 1-2 (только postgres_exporter). Ключевой инсайт: **соединения освобождаются сразу** после снижения нагрузки — Go `sql.DB` возвращает их в пул. Восстановление мгновенное.
- **Query Duration** — P95 <30ms на пиках. Для сравнения: при storm те же запросы занимали 5000ms.

**Node Exporter Full**:
- **CPU** — три чётких пика ~15-20%, между ними возврат к baseline ~2%. Система не накапливает тепловую нагрузку между пиками.
- **Memory** — абсолютно ровная линия. Утечек памяти нет, GC справляется.

## 6. Найденные боттлнеки

| # | Боттлнек | Симптом (метрика) | Сценарий |
|---|---|---|---|
| 1 | **Postgres connection exhaustion** — `max_connections=200`, backend без `MaxOpenConns` | error_rate=24.77%, P95=6.93s, RPS деградирует при >200 параллельных запросов | storm |
| 2 | **Отсутствие connection pool лимита в Go** — `sql.DB` открывает неограниченное число соединений, упираясь в лимит postgres | `pq: sorry, too many clients already` ошибки под пиком | storm |
| 3 | **GET /api/orders без пагинации** — возвращает LIMIT 100 записей, при высокой нагрузке создаёт конкурирующий sequential scan | get_order_latency avg=2153ms при storm vs 17ms при pulse | storm |
| 4 | **Нет read replica / cache** — GET и POST конкурируют за одни и те же соединения к одному postgres | Latency GET и POST деградируют синхронно | storm, wave |
| 5 | **Единственная реплика backend** — вертикальное масштабирование не работает при исчерпании postgres | CPU backend не является узким местом, но масштабирование go-процесса не поможет без решения #1 | storm |

## 7. Решения

| Боттлнек | Решение | Почему поможет |
|---|---|---|
| Postgres connection exhaustion | Добавить **PgBouncer** (transaction pooling) между backend и postgres | PgBouncer мультиплексирует N app-соединений в M postgres-соединений (M << N). 1000 VU → 20-50 реальных PG-соединений |
| Отсутствие лимита пула в Go | Добавить `db.SetMaxOpenConns(50)` и `db.SetMaxIdleConns(10)` в `main.go` | Предотвращает thundering herd на postgres; очередь формируется в app, а не в postgres |
| GET без кэша | Добавить **Redis cache** с TTL=5s для `GET /api/orders` | Популярные листинги отдаются из памяти, снимая нагрузку с postgres для read-heavy трафика |
| Нет read replica | Добавить **postgres read replica** (streaming replication) и маршрутизировать GET-запросы на неё | SELECT-запросы идут на replica, INSERT — на primary; вдвое увеличивает пропускную способность по чтению |
| Единственный backend | **Горизонтальное масштабирование** — запустить 2-3 backend реплики за nginx upstream | nginx балансирует нагрузку; CPU backend перестаёт быть узким местом; нужен PgBouncer чтобы 3×50 conn не упёрлись в postgres |
| GET LIMIT 100 без индекса | Добавить `CREATE INDEX orders_created_at_idx ON orders(created_at DESC)` | Покрывающий индекс превращает sequential scan в index scan; latency GET снижается на порядок при большом числе записей |
