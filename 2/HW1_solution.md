Concert Comparison

A concert ticketing site with big acts and high volume needs an elastic solution to sell tickets.

Users: thousand of concurrent users, bursts of up to 10,000/second when tickets go on sale

Requirements:

allow concurrent ticket buying

do not sell a seat more than once!

shoppers can see an overview of remaining seats

Additional Context:

consider an implementation in both Space Based and Microservices architecture style

identify the tradeoffs for each solution

## 2. Scope Refinement

### 2.1 Границы системы

```
[Пользователи]              [Платформа]                      [Внешние сервисы]
  - Покупатель        ──►    - Каталог событий          ──►   - Платёжный шлюз (СБП/эквайринг)
  - Организатор       ──►    - Схема зала (seat map)    ──►   - Email / SMS (билеты, уведомления)
  - Администратор     ──►    - Инвентарь билетов        ──►   - Облачное хранилище (PDF билеты)
                             - Корзина + резервирование  ──►  - Anti-bot / CAPTCHA сервис
                             - Оформление заказа
                             - Выдача электронных билетов
```

### 2.2 Обязательные требования

1. Каталог концертов с поиском и фильтрацией
2. Интерактивная схема зала с актуальным статусом мест
3. Резервирование места на время оформления заказа
4. Гарантия: одно место продаётся ровно одному покупателю
5. Оформление заказа и интеграция с платёжным шлюзом
6. Выдача электронного билета (QR-код) после оплаты
7. История заказов покупателя
8. Управление событиями и залами для организатора
9. Защита от ботов (rate limiting, CAPTCHA при старте продаж)
10. Очередь при перегрузке (virtual waiting room)

### 2.3 Необязательные требования

1. Лучшие места автоматически
2. Групповые покупки (несколько мест рядом автоматически)
3. Уведомления о появлении билетов
4. Мобильное приложение
5. Программа лояльности

### 2.4 Скрытые зависимости

- **Бронь + таймаут** — место должно автоматически освобождаться при истечении таймера корзины. Требует надёжного механизма TTL (Redis TTL / distributed scheduler).
- **Пик при старте продаж** — 10 000 запросов/секунду в первые минуты. Это в ~600 раз выше среднего трафика. Архитектура должна выдерживать эту нагрузку без потери данных.
- **Идемпотентность платежей** — если пользователь нажал "оплатить" дважды, списание должно произойти ровно один раз.
- **Схема зала** — тяжелый на чтение объект: тысячи пользователей смотрят схему одновременно. Нужен кэш, но с инвалидацией при изменении статуса мест.
- **Anti-scalping** — лимит на количество билетов в одни руки должен проверяться по user_id и по платёжным данным (одна карта ≠ разные аккаунты).
- **Virtual waiting room** — без очереди при старте продаж сервис ляжет. Пользователи должны получить позицию в очереди и ждать своей очереди.

## 3. Функциональные требования

### 3.1 Роли пользователей

| Роль | Описание |
|---|---|
| **Гость** | Просматривает каталог, схему зала. Не может покупать |
| **Покупатель (Buyer)** | Зарегистрированный пользователь. Выбирает места, оформляет заказ |
| **Организатор (Organizer)** | Создаёт события, загружает схему зала, управляет ценовыми зонами, запускает продажи |
| **Администратор** | Управляет платформой, пользователями, мониторинг |

### 3.2 Сценарии взаимодействия

#### Гость
- Просмотр каталога концертов (поиск, фильтр по городу / дате / жанру)
- Просмотр страницы события (описание, дата, схема зала, цены)
- Просмотр схемы зала (без возможности выбора мест)
- Регистрация / вход

#### Покупатель
- Авторизация
- Просмотр каталога и события
- Просмотр интерактивной схемы зала (цвет = статус места)
- Выбор места → место уходит в бронь на 10 минут
- Оформление заказа (персональные данные, подтверждение)
- Оплата через внешний шлюз
- Получение электронного билета (email + личный кабинет)
- Просмотр истории своих заказов
- Отмена бронирования (до оплаты — автоматически по таймауту)

#### Организатор
- Создание события (название, дата, место, описание)
- Загрузка / настройка схемы зала (секции, ряды, места, ценовые зоны)
- Установка дат и условий старта продаж
- Мониторинг продаж в реальном времени
- Ручное управление местами (блокировка, VIP-бронь)

#### Администратор
- Управление организаторами и событиями
- Мониторинг нагрузки и состояния системы
- Управление очередью (virtual waiting room)
- Работа с инцидентами

### 3.3 CRUD по основным сущностям

| Сущность | Create | Read | Update | Delete |
|---|---|---|---|---|
| Пользователь | Регистрация | Профиль | Редактирование | Деактивация |
| Событие | Организатор | Все роли | Организатор (до старта продаж) | Организатор (до старта) |
| Схема зала | Организатор | Все роли | Организатор (до старта) | Организатор (до старта) |
| Место (Seat) | Система (из схемы) | Все роли | Система (статус: available/held/sold) | — |
| Заказ (Order) | Покупатель | Покупатель, Организатор | Система (статус оплаты) | Отмена (только бронь) |
| Билет (Ticket) | Система (после оплаты) | Покупатель | — | — |

### 3.4 Corner Cases

- **Два пользователя выбирают одно место одновременно** — атомарная бронь через лок или Redis SET NX. Второй получает ошибку "место занято".
- **Таймер корзины истёк, но оплата прошла** — если деньги списаны после истечения брони, нужна компенсирующая транзакция: возврат средств, уведомление пользователя.
- **Оплата зависла** — место остаётся в бронь до получения webhook от платёжного шлюза. Таймер продлевается до 30 минут для pending-статуса.
- **10 000 RPS в первую секунду** — без virtual waiting room и rate limiting сервис упадёт. Все запросы сверх лимита идут в очередь, пользователь видит позицию.
- **Пользователь открыл несколько вкладок** — бронь привязан к сессии/user_id, дублирующая попытка выбрать то же место игнорируется.
- **Организатор загрузил неверную схему зала** — нельзя менять схему после старта продаж; нужен процесс подтверждения схемы до публикации.
- **Платёжный шлюз недоступен** — заказ в статусе pending, место в бронь, retry с exponential backoff. Уведомление пользователю.
- **Массовая отмена события** — все sold билеты переходят в статус refund, автоматический возврат через платёжный шлюз, уведомления.
- **Скальпер с множеством аккаунтов** — fingerprinting устройства, лимит по платёжным реквизитам, rate limiting по IP.

### 6.2 Сессии и запросы по ролям — обычный день

#### Гость

| Шаг сессии | HTTP-запросы |
|---|---|
| Каталог + поиск | 4 |
| Страница события | 3 |
| Схема зала (статичная) | 2 |
| Прочие (pagination) | 2 |
| **Итого** | **~11** |

- Сессий в день: 1.5
- **RPD (гость) = 12 000 × 1.5 × 11 = 198 000**

#### Покупатель

| Шаг сессии | HTTP-запросы |
|---|---|
| Авторизация | 2 |

| **Итого** | **~20** |

- **RPD (покупатель) = 7 000 × 1.2 × 20 = 168 000**

#### Организатор + Администратор

- RPD (организатор) = 200 × 1 × 30 = 6 000

### 6.4 День старта продаж — Event Day расчёт

#### Покупатель (180 000 DAU)

В день старта продаж покупатель делает больше попыток (конкуренция за места):

| Шаг сессии | HTTP-запросы |
|---|---|
| Авторизация (заранее) | 2 |
| Ожидание в virtual waiting room | 1 (polling каждые 5 сек → WS) |
| Схема зала (обновления) | 5 (обновляется агрессивно) |
| Попытки выбора мест (3–5 попыток из-за конкуренции) | 10 |
| Оформление и оплата | 4 |
| Получение билета | 2 |
| **Итого** | **~24** |

- Сессий в день: 1 (пришёл за билетом — это разовое событие)
- **RPD (покупатель, Event Day) = 180 000 × 1 × 24 = 4 320 000**

#### Гость (300 000 DAU) — в основном смотрят, не покупают

- Сессий: 1, запросов: 12
- **RPD (гость, Event Day) = 300 000 × 1 × 12 = 3 600 000**

#### Итого RPD — Event Day

```
RPD = 4 320 000 + 3 600 000 + 7 000 (орг.) ≈ 7 927 000
Средний RPS (Event Day) = 7 927 000 / 86 400 ≈ 92 RPS
```

### 6.5 Пиковая нагрузка

#### Метод 1 — Пиковое временное окно Event Day

Старт продаж — объявленное время (например, 10:00). Все покупатели заходят одновременно. Допускаем, что **70% трафика Event Day** концентрируется в первом **1-часовом окне**.

```
Трафик в пике = 7 927 000 × 0.70 = 5 549 000 запросов
Длина окна    = 1 час = 3 600 секунд
RPS Peak (1 час) = 5 549 000 / 3 600 ≈ 1 540 RPS
```

#### Метод 2 — Условие задачи (bursts up to 10 000 RPS)

Задача явно указывает: **bursts of up to 10 000 RPS** в момент открытия продаж.

Это всплеск нагрузки длительностью 30–120 секунд, затем нагрузка спадает до ~1 000–2 000 RPS по мере того, как места разбираются.

#### Итоговые целевые значения

| Метрика | Обычный день | Event Day (пик) | Event Day (всплеск нагрузки) |
|---|---|---|---|
| Средний RPS | ~4 RPS | ~92 RPS | **10 000 RPS** |
| Одновременных пользователей | ~2 000 | ~50 000 | ~200 000 |
| бронь-операций в секунду | ~1 | ~200 | **~5 000** |
| Чтений схемы зала в секунду | ~10 | ~500 | **~8 000** |

> Соотношение пик/средний = **10 000 / 4 ≈ 2 500×** — экстремальный показатель, требующий принципиально разного подхода к архитектуре.

## 7. Архитектурные стили: Microservices vs Space-Based

### 7.1 Microservices Architecture

#### Ключевые сервисы

```
[API Gateway + Rate Limiter]
       │
       ├── User Service          (регистрация, авторизация, профиль)
       ├── Event Service          (каталог событий, схема зала)
       ├── Inventory Service      (инвентарь мест, бронь, статус) ← КРИТИЧЕСКИЙ
       ├── Order Service          (оформление заказа, история)
       ├── Payment Service        (интеграция с шлюзом, idempotency)
       ├── Ticket Service         (генерация PDF, QR-кодов)
       ├── Notification Service   (email, SMS)
       └── Queue Service          (virtual waiting room)
```

#### Как решается проблема двойной продажи

Inventory Service является единственным источником истины по статусу мест. бронь — атомарная операция через Redis с SET NX (установить только если не существует) + TTL. Одновременно сотни инстансов Inventory Service работают параллельно, но все обращаются к одному Redis-кластеру.

```
Client → API Gateway → Inventory Service → Redis SET NX seat:{id} user:{id} EX 600
                                                          ↓
                                              OK → место забронировано
                                              FAIL → место уже занято
```

#### Масштабирование под 10 000 RPS

- API Gateway: горизонтальное масштабирование, rate limiting
- Inventory Service: горизонтальное масштабирование (stateless), узкое место — Redis
- Redis Cluster: шардинг по seat_id, ~100 000 операций/сек на узел → достаточно
- Event Service / схема зала: агрессивное кэширование (CDN + Redis read-through), ~95% запросов не доходят до БД
- Virtual Waiting Room: отдельный сервис с очередью (Kafka / Redis Streams)

#### Трейдоффы Microservices

| Плюсы | Минусы |
|---|---|
| Независимое масштабирование каждого сервиса | Распределённые транзакции (Saga pattern) — сложно |
| Независимый деплой и обновление | Latency растёт на каждом hop между сервисами |
| Технологическая гетерогенность (Go для Inventory, Python для Notification) | Операционная сложность (service discovery, distributed tracing, Circuit Breaker) |
| Понятная граница ответственности | Сложная отладка distributed failures |
| Хорошо масштабируется горизонтально | Требует зрелой DevOps-культуры и инфраструктуры |

### 7.2 Space-Based Architecture (SBA)

#### Принцип

Space-Based Architecture устраняет централизованную базу данных как узкое место. Данные распределяются по **Processing Units (PU)** — узлам, каждый из которых содержит:
- In-memory data grid (копию нужных данных)
- Бизнес-логику
- Локальный кэш

Узлы общаются через **Virtual Shared Space** (распределённое in-memory хранилище, например Apache Ignite / Hazelcast).

#### Применение к ticketing

```
[Клиент] → [Load Balancer] → [Processing Unit N]
                                    │
                         ┌──────────┴──────────┐
                         │  In-Memory Grid     │  ← статус всех мест события
                         │  (Ignite / Hazel.)  │  ← партиция по event_id
                         │  Бизнес-логика      │
                         └──────────┬──────────┘
                                    │
                         [Async Persistence]  ← пишет в БД асинхронно
                         (Kafka → PostgreSQL)
```

Каждый Processing Unit берёт **партицию событий** (например, PU-1 обслуживает concert_id 1–100, PU-2 — 101–200). Запрос на бронь места маршрутизируется к нужному PU. Внутри PU операция — локальная, без сетевых вызовов к БД.

#### Как решается проблема двойной продажи

В SBA двойная продажа исключается за счёт **Single-Writer** принципа: каждое место обслуживается ровно одним Processing Unit. Нет распределённых локов — нет гонки. Операция бронь — это атомарное обновление in-memory структуры внутри одного PU.

#### Масштабирование под 10 000 RPS

- Добавление новых Processing Units (horizontal scale)
- Каждый PU обслуживает свою партицию и держит данные в памяти
- 10 000 RPS / N PU: при 20 PU — 500 RPS на PU, что тривиально для in-memory операции
- Scale-out < 30 секунд (новый PU берёт партицию данных из shared space)

#### Трейдоффы Space-Based Architecture

| Плюсы | Минусы |
|---|---|
| Экстремальная throughput (всё в памяти, нет обращений к БД на горячем пути) | Высокая стоимость RAM (in-memory data grid дорог) |
| Нет узкого места в виде центральной БД | Сложность перебалансировки партиций |
| Линейное масштабирование: добавляем PU — растёт throughput | Асинхронная персистентность → риск потери данных при падении PU до flush |
| Единственный writer для партиции → нет distributed locks | Более редкий паттерн → меньше готовых решений, сложнее нанять команду |
| Отличная эластичность под всплеск нагрузкии | Сложнее делать cross-partition запросы (например, история заказов по всем событиям) |

### 7.3 Сравнительная таблица

| Критерий | Microservices | Space-Based |
|---|---|---|
| **Пиковый throughput** | Высокий (ограничен Redis / DB) | Экстремальный (in-memory) |
| **Latency на бронь** | ~5–20 мс (сеть + Redis) | < 1 мс (локальная память) |
| **Корректность (no double-sell)** | Через Redis SET NX | Через Single-Writer PU |
| **Эластичность** | Хорошая (scale per service) | Отличная (add PU in seconds) |
| **Стоимость инфраструктуры** | Средняя | Высокая (RAM) |
| **Операционная сложность** | Высокая | Очень высокая |
| **Время разработки MVP** | Быстрее | Медленнее |
| **Зрелость экосистемы** | Высокая | Средняя |
| **Подходит для** | Большинство концертов (< 5 000 RPS) | Мегаконцерты (10 000+ RPS, Taylor Swift эффект) |

---

### 7.4 Рекомендация

**Для MVP и большинства сценариев — Microservices.**
Inventory Service с Redis SET NX покрывает корректность, горизонтальное масштабирование покрывает нагрузку, virtual waiting room сглаживает всплеск нагрузкии.

**Для масштаба 10 000+ RPS без waiting room — Space-Based.**
Если бизнес-требование: "все 10 000 пользователей обслуживаются мгновенно без очереди" — тогда SBA является архитектурно правильным выбором, несмотря на стоимость и сложность.

**Гибридный путь:** Microservices-архитектура с Space-Based Inventory Service. Только критический инвентарный слой переносится на in-memory grid (Hazelcast Embedded в Inventory Service), остальные сервисы остаются классическими.
